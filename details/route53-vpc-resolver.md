## 名前について

2025 年 11 月に Route 53 Global Resolver（プレビュー）が発表されたときに、**Route 53 Resolver** から **Route 53 VPC Resolver** に名前が変わりました。機能は同じです。教材や過去問では、旧名の「Route 53 Resolver」で出てくることが多いので、どちらの名前でも分かるようにしておきましょう。

## しくみ

DNS には役割の違う 2 つの部品があります。

| 部品 | 役割 | AWS では |
|---|---|---|
| 権威 DNS サーバー | 「このドメインの答え（IP アドレス）はこれ」と**登録・回答**する | [[route53]] のホストゾーン |
| **リゾルバー** | 利用者の代わりに**問い合わせて答えを探してくる** | **Route 53 VPC Resolver** |

VPC Resolver は、**すべての VPC に最初から用意されている**リゾルバーです（「Amazon Provided DNS」とも呼ばれます）。VPC 内の EC2 などが名前解決をすると、ここに問い合わせが届きます。

- 問い合わせ先の IP アドレス：**VPC の CIDR の先頭 + 2**（例：`10.0.0.0/16` なら `10.0.0.2`）。どのインスタンスからでも `169.254.169.253` でも届く
- 答えられるもの
  - インターネット上の公開ドメイン名
  - VPC 内のリソースの名前（EC2 の内部ホスト名など）
  - VPC に関連付けた [[route53]] の**プライベートホストゾーン**のレコード
- VPC の設定 **enableDnsSupport**（DNS 解決）を有効にしておく必要がある。プライベートホストゾーンを使うには **enableDnsHostnames**（DNS ホスト名）も有効にする

## オンプレミスとつなぐ：エンドポイントと転送ルール（最重要）

標準の VPC Resolver は、VPC の中からしか使えません。オンプレミスとの間で名前解決をするには、**エンドポイント**を作ります。エンドポイントは、指定したサブネットに IP アドレス付きの ENI として作られます（可用性のため、**2 つ以上の AZ** に置く）。

| エンドポイント | 通信の向き | 使い方 | 試験でこう出たら |
|---|---|---|---|
| **インバウンドエンドポイント** | **オンプレミス → VPC** | 社内の DNS サーバーから、VPC 内の名前の問い合わせをエンドポイントの IP アドレスに転送してもらう | 「社内のサーバーから、プライベートホストゾーンのレコードを解決したい」 |
| **アウトバウンドエンドポイント** | **VPC → オンプレミス** | **転送ルール**（例：`corp.example.com` は社内の DNS サーバー `192.168.0.10` へ）を作って VPC に関連付ける | 「VPC 内の EC2 から、社内のドメイン名を解決したい」 |

覚え方：「インバウンド／アウトバウンド」は **VPC から見た向き**です。VPC に入ってくる問い合わせがインバウンド、VPC から出ていく問い合わせがアウトバウンドです。

- オンプレミスとの通信には、[[direct-connect]] か [[site-to-site-vpn]] での接続が必要
- **転送ルール**は、AWS Resource Access Manager（RAM）で**他のアカウントと共有**できる。[[organizations]] の多数のアカウントの VPC で、同じルールを使える
- エンドポイントには料金がかかる（ENI ごとの時間料金＋問い合わせ数）

## その他の機能

| 機能 | 内容 | 試験でこう出たら |
|---|---|---|
| **DNS Firewall** | VPC から出ていく DNS の問い合わせを、ドメインのリスト（AWS が用意した悪質なドメインのリストも使える）で**許可・ブロック**する | 「悪意のあるドメインへの名前解決を防ぎたい」「DNS を使ったデータの持ち出しを防ぎたい」 |
| **クエリログ** | VPC 内からの DNS の問い合わせを記録し、[[cloudwatch]] Logs・[[s3]]・[[data-firehose]] に保存する | 「どのインスタンスが、どのドメインを問い合わせたかを記録したい」 |

## Global Resolver との違い

2025 年 11 月に発表された **Route 53 Global Resolver**（プレビュー）は、VPC の外（オフィスやリモートの利用者など）からも、エニーキャストで使えるリゾルバーです。VPC Resolver は名前のとおり VPC のためのリゾルバーです。SAA-C03 で問われるのは主に VPC Resolver（旧 Route 53 Resolver）のほうです。

## 試験でのポイント

- 「オンプレミスから VPC 内のプライベートなドメイン名を解決」→ **インバウンドエンドポイント**
- 「VPC 内から、オンプレミスのドメイン名を解決」→ **アウトバウンドエンドポイント＋転送ルール**
- 「両方向」→ インバウンドとアウトバウンドの**両方**を作る
- 「複数のアカウントの VPC で、同じ転送ルールを使いたい」→ **RAM で転送ルールを共有**
- 「最小の運用負荷で」→ EC2 に DNS サーバー（BIND など）を自分で立てる選択肢より、VPC Resolver のエンドポイントが正解になりやすい

## よくあるひっかけ

- インバウンドとアウトバウンドの向きを逆に覚えてしまう。**VPC から見た向き**で考える
- [[route53]] の**パブリック**ホストゾーンにレコードを登録すると、社内向けの名前がインターネットに公開されてしまう。社内だけで使う名前はプライベートホストゾーン
- プライベートホストゾーンを作ったのに名前解決できない → VPC への関連付けと、enableDnsSupport・enableDnsHostnames の設定を確認する
- DHCP オプションセットで、インスタンスの DNS サーバーを社内の DNS サーバーに変える方法もあるが、その場合インスタンスは VPC Resolver に問い合わせなくなり、プライベートホストゾーンなどを直接引けなくなる。社内の DNS と両方使いたいなら、エンドポイントと転送ルールで組み合わせる
