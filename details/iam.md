## しくみ

AWS アカウントの中で、**誰が（認証）**・**何をしてよいか（認可）**を管理します。グローバルなサービスで、無料です。

| 要素 | 内容 |
|---|---|
| **ユーザー** | 人やアプリに対応する長期的な ID。パスワードやアクセスキーを持つ |
| **グループ** | ユーザーの集まり。グループにポリシーを付けると、所属するユーザー全員に効く |
| **ロール** | 一時的に引き受ける（AssumeRole）権限のセット。長期の認証情報を持たない |
| **ポリシー** | 許可・拒否を書いた JSON の文書 |

## ポリシーの評価ルール（頻出）

1. 標準ではすべて**拒否**（暗黙の拒否）
2. どこかで**許可**されていれば許可
3. どこかで**明示的に拒否**されていれば、許可があっても**拒否が勝つ**

ポリシーの種類：アイデンティティベース（ユーザー・グループ・ロールに付ける）、**リソースベース**（S3 バケットポリシーなど、リソース側に付ける）、**アクセス許可の境界**（与えられる権限の上限）、[[organizations]] の **SCP**

## ロールの使いどころ

- **EC2 から S3 にアクセス**：アクセスキーをサーバーに置かず、EC2 に **IAM ロール（インスタンスプロファイル）** を付ける
- **別のアカウントへのアクセス**：相手のアカウントのロールを引き受ける（クロスアカウントロール）
- **外部の ID でログイン**：SAML や OIDC の ID プロバイダーと連携する（フェデレーション）
- 一時的な認証情報は **AWS STS** が発行する

## ベストプラクティス

- **ルートユーザーは日常的に使わない**。MFA を設定し、アクセスキーは作らない
- **最小権限**：必要な権限だけを与える（IAM Access Analyzer で使っていない権限を見つける）
- ユーザーには **MFA**
- 人のアクセスは [[iam-identity-center]] にまとめるのがおすすめ

## 試験でのポイント

- 「アプリ（EC2・Lambda・ECS）に AWS の権限を与えたい」→ **IAM ロール**。アクセスキーをコードや設定ファイルに書く選択肢は誤り
- 「別のアカウントのリソースにアクセスさせたい」→ **クロスアカウントロール**
- 「開発者が自分に強い権限を付けられないようにしたい」→ **アクセス許可の境界**
- 明示的な拒否は、どの許可よりも優先される

## よくあるひっかけ

- IAM はアプリの**利用者（会員）**を管理するものではない。それは [[cognito]]
- IAM グループの中にグループは入れられない。グループはロールのように「引き受ける」ものでもない
