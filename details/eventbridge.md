## しくみ

**イベント**（「何かが起きた」という JSON のメッセージ）を**イベントバス**で受け取り、**ルール**に合うものを**ターゲット**に届けます（旧 CloudWatch Events）。

- **イベントの発生元**：AWS のサービス（EC2 の状態変化、S3 へのアップロード、[[guardduty]] の検出など）、SaaS（Zendesk、Datadog など）、自分のアプリ
- **ターゲットの例**：[[lambda]]、[[step-functions]]、[[sqs]]、[[sns]]、[[ecs]] のタスク、API の呼び出し
- **ルール**：イベントの内容（イベントパターン）で絞り込む
- **EventBridge Scheduler**：cron のように、決まった時刻・間隔で処理を起動する
- **Pipes**：送信元とターゲットを 1 対 1 でつなぎ、途中で絞り込み・加工する
- **アーカイブと再生**：過去のイベントを保存し、後から流し直す
- **スキーマレジストリ**：イベントの形を管理する

## 試験でのポイント

- 「AWS サービスのイベントに反応して自動で処理」「EC2 が停止したら通知」→ EventBridge
- 「毎日決まった時刻に Lambda を実行」「cron の代わり」→ EventBridge（Scheduler）
- 「SaaS のイベントを取り込みたい」→ EventBridge のパートナーイベントソース
- [[cloudtrail]] に記録された API 操作をきっかけにすることもできる（例：セキュリティグループが変更されたら通知）

## よくあるひっかけ

- 単純に複数の宛先へ通知するだけなら [[sns]] でもよい。「イベントの内容で振り分けたい」「SaaS」「スケジュール」が EventBridge を選ぶ決め手
- メッセージをためて、受け取る側が自分のペースで処理するのは [[sqs]]
